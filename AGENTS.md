# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable Product Decisions

- Before token or session limits could interrupt validated work, create a safe Git checkpoint. Exclude `node_modules/`, caches, `dist`/build artifacts, and all secrets unless the user explicitly requests otherwise.
- The approved prototype direction is the Executive Ledger experience: restrained graphite surfaces, warm metallic accents, editorial typography, evidence-linked intelligence, and executive-level information density. Preserve this visual language unless the user explicitly changes direction.
- "Ask your meetings" (meeting chat) has its own page at `#/ask` (2026-10-06, user feedback), laid out like the recording studio: conversation in the main column with a composer that stays at the bottom, and a rail explaining scope, search mode, answer provider, and history. The workspace links to it from its header and from a card below the meetings list; do not embed the chat back into the workspace.
- Speech-to-text is local Whisper running on our own server (2026-10-03): meeting audio never leaves the machine. Do not switch to a cloud speech service without the user's explicit decision.
- The summary, decisions, risks, questions, and action plan are written by Claude through the Anthropic API (2026-10-03). Only transcript text, participant IDs, and the meeting date are sent; credentials stay server-side and never reach the browser.
  - Revised 2026-10-06 (user decision): the transcript sent to Claude also carries the anonymous per-meeting speaker labels (`SPEAKER_00`, ...), renumbered by first appearance. Never names, voice data, or raw worker labels. Claude may attach a label to an action as the unverified speaker who took it on; a label is never an owner, identity, or participant ID.
  - Each action carries `committed` (someone agreed) or `proposed` (suggested, not taken on), taken only from what was said.
- OpenAI is an approved alternative summary provider (2026-10-06, user decision; chosen because the account has OpenAI credit). `MEETING_SUMMARY_PROVIDER=openai` selects it; it receives exactly the same fields as Claude through the Responses API with `store: false` and a strict JSON schema, and its output is re-validated the same way. Claude remains available. A chosen provider without credentials falls back to transcript-only, never to the other provider. Real-meeting use of either provider still needs its organizational approval (`docs/security/openai-api-processing-approval.md`, `docs/security/anthropic-api-processing-approval.md`).
- Local storage is durable (2026-10-03): meetings, consent, transcripts, action plans, and audit persist in a SQLite file in the Git-ignored `.data/` folder (built-in `node:sqlite`). Recording audio is encrypted with AES-256-GCM using a generated key file in `.data/keys/`. Never commit `.data/`. Production still moves to PostgreSQL, object storage, and KMS.
- Production storage is self-hosted PostgreSQL (2026-10-03), selected by `DATABASE_URL`.
  - The server connects as a least-privilege role (never a superuser, a `BYPASSRLS` role, or the table owner).
  - Row-level security per tenant is enforced by the database.
  - Recording audio is AES-256-GCM encrypted with an operator-supplied key file (`MEETING_AUDIO_KEY_FILE`).
  - Migrations run only through `npm run db:migrate` as the owner.
  - See `docs/architecture/self-hosted-postgres.md`. The user has decided to keep PostgreSQL local on Windows; use the self-hosted deployment and treat Supabase or another hosted database as out of scope unless this decision is revised.
- Microsoft Entra integration is deferred until the company formally decides to roll this app out. Until then, keep the working end-to-end pipeline restricted to this machine (loopback only) with its development identity headers; do not expose the API on a LAN or deploy it.
- Microsoft Teams is the first meeting-platform integration. Do not retain Zoom routes, UI, terminology, or claims. Keep the Teams connector explicitly unconnected until a production server-side Entra/OAuth application and secret-manager configuration exist.
- The current self-hosted PostgreSQL operating target is Windows. Keep the delivery loopback-only until Microsoft Entra identity is implemented; durable database storage does not authorize wider access.
- The user approved per-computer, local-only prototype distribution (2026-10-06). Each Windows installation must have independent PostgreSQL roles/database, `.env`, encrypted-audio key, durable data, and local model cache; never copy these between computers or expose an instance beyond `127.0.0.1`. This is evaluation-only, not a shared deployment or a substitute for Entra.
- Meeting chat (RAG) is approved for development (2026-10-06, user decision): answers are written by OpenAI or Claude, retrieval is lexical (keyword) across every meeting the asker may read, and chat history is saved per user.
  - It is a separate data flow from summaries and stays off unless `MEETING_CHAT_PROVIDER` names a provider. A provider receives only the question, at most 12 citation-sized excerpts labelled with anonymous meeting letters and dates, and up to 4 earlier readable turns: never IDs, titles, names, or audio. Real-meeting use needs the chat section of the provider's approval packet.
  - Saved turns record every meeting they drew on; they are hidden (and never sent as context) while the user cannot read any of those meetings, and deleted with any of them.
  - Retrieval is hybrid (2026-10-06, user decision): keyword matches fused with meaning-based matches from a local `bge-m3` embedding model served by Ollama on this computer (loopback only; meeting text is never sent anywhere to be embedded). Vectors live in the app database (`knowledge_embeddings`, tenant RLS in PostgreSQL), are built lazily only for meetings the asker may read, are cleared whenever a meeting's knowledge is replaced, quarantined, or deleted, and fall back to keyword retrieval when Ollama or migration 003 is unavailable. Move to pgvector only when volume requires it.
  - Chat has an explicit guardrail layer (`server/guardrails.js`, 2026-10-07, user decision): question validation and a per-user daily limit (`MEETING_CHAT_DAILY_LIMIT`, default 200); personal-data redaction (emails, phones, ID/case/card/long numbers) of every excerpt and earlier turn sent to a provider; only valid citations kept; a grounding check that flags answer numbers absent from what was sent and statements far from their cited sources (local bge-m3), withholding an answer with no grounded statement. Triggered guardrails are audited by code only. Topic restriction is not built: it needs a product decision.
  - Chat has an explicit memory layer (`server/chat-memory.js`, 2026-10-07, user decision): the last 4 readable turns as working memory, plus up to 2 older related turns recalled by local bge-m3 similarity (no extra provider call); history expires after `MEETING_CHAT_RETENTION_DAYS` (default 90) and the retention sweep deletes it; users can forget one turn or clear all. Memory vectors stay server-side and are never returned to the browser.
- Speaker naming is approved (2026-10-07, user decisions). Diarization still produces anonymous labels only, and nothing is named automatically; a person may confirm which meeting participant a label is, per recording:
  - The organizer names or corrects any label; any other participant may claim an unnamed label only as themselves; the named person can dispute (remove) it, after which the organizer cannot restore that same pairing. Every change is versioned, kept in history, and audited without content.
  - Names are display only: they appear in the transcript, meeting knowledge, exports, chat sources, and as the speaker of an action, and never change an action's owner.
  - Confirmed names (participant IDs) are sent with chat excerpts to the chat provider; unconfirmed labels stay anonymous. A first summary is written before anyone can name a speaker; when the organizer rewrites a summary (user decision 2026-10-07), confirmed names are sent to the summary provider as "SPEAKER_01, confirmed as sam".
  - An action keeps an owner only if that participant ID is named in the transcript lines the action cites; being the (confirmed) speaker never makes someone the owner. This is enforced in normalization, not only in the prompt.
- Summary regeneration (CAP-10, 2026-10-07, user decision): the organizer can rewrite a processed recording's summary, decisions, risks, questions, and action plan from its stored transcript. The result passes the same normalization as first processing, gets versioned IDs, and the previous three versions are kept (and wiped on deletion or quarantine) so dropped items are visible. Regeneration requires an active, recordable meeting with unchanged policy and every required participant's latest consent decision still "granted"; an expired consent window alone does not block it, because nothing new is captured (decision by Claude, for the user's review).
- The local pyannote Community-1 diarization pilot is approved (2026-10-06). It may emit anonymous, per-meeting speaker labels only; never voiceprints or automatic names. Acquire its gated model through a controlled operator action with a least-privilege Hugging Face token, then run offline from the protected local model directory. Never commit, log, or put that token in `.env`.
